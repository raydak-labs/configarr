# Sonarr v5 beta: Configarr compatibility research

**Research snapshot:** 2026-10-12  
**Scope:** Official Sonarr v5 beta announcement and API artifacts, with a comparison to the v3 API specification used by Sonarr v4, followed by implementation and runtime verification against a pinned v5 beta.

**Date caveat:** The available session date is 2025-03-08, but the official forum page identifies the beta announcement as 2026-10-12. The page and API artifacts are live and currently retrievable, but they are future-dated relative to the session date; treat the beta as a future-referenced source here, not as a release that can be verified as already announced as of 2025-03-08.

## Executive summary

Supporting Sonarr v4 and v5 concurrently appears feasible, but it is not a “change `/api/v3` to `/api/v5`” update. Sonarr v5 documents a new API version and the v5 OpenAPI spec changes configuration routes, some resource names and fields, request parameters, and quality-definition behavior. Many core payloads remain structurally similar, but Configarr’s current Sonarr client is built directly on the v3-generated client and exposes those generated v3 resource types.

The likely implementation is a Sonarr-version-aware client dispatch with separately generated v3/v5 API clients, followed by type-safe adapters for the changed resources. Quality definitions, download-client save/test behavior, release-profile indexers, and the renamed settings endpoints deserve particular attention. The beta OpenAPI artifact is useful evidence, but it is from the moving `v5-develop` branch; compatibility and semantics should be confirmed against a pinned beta build before shipping.

## Source set and version context

The official v5 beta announcement was posted by Sonarr developer `markus101` on **2026-10-12**. It describes the beta as launching on the `develop` branch, lists a new API v5 and expanded API functionality, and warns that a v4 backup is needed to roll back. Its highlighted changes include more powerful release profiles that can apply to multiple indexers. [Sonarr v5 beta announcement (2026-10-12)](https://forums.sonarr.tv/t/sonarr-v5-beta/41099)

Sonarr publishes separate generated OpenAPI artifacts:

- [Sonarr v3 OpenAPI JSON (`develop`, API version 3.0.0)](https://raw.githubusercontent.com/Sonarr/Sonarr/develop/src/Sonarr.Api.V3/openapi.json). Its own description says the v3 API docs apply to Sonarr v3 and v4, with some features limited to v4.
- [Sonarr v5 OpenAPI JSON (`v5-develop`, API version 5.0.0)](https://raw.githubusercontent.com/Sonarr/Sonarr/v5-develop/src/Sonarr.Api.V5/openapi.json). Its description says the v5 docs apply to Sonarr v5 only.
- [Published Sonarr API docs](https://sonarr.tv/docs/api/index) select the v3 API docs for v3/v4; [the v5 API docs](https://sonarr.tv/docs/api/?api=v5) are separately selectable.

The branch-based raw JSON links are **rolling snapshots**, not immutable release artifacts. This comparison uses their contents as retrieved on 2026-10-12; regenerate the comparison against a pinned v5 beta commit/build during implementation.

For historical context, the v4 launch announcement (2023-12-30) described a major release with a backward-incompatible database migration, removal of the v2 API, and Quality Size Preference among its changes. [Sonarr v4 release announcement (2023-12-30)](https://forums.sonarr.tv/t/sonarr-v4-released/33089)

The beta announcement independently confirms a new API v5 and expanded API functionality, including multi-indexer release profiles ([announcement](https://forums.sonarr.tv/t/sonarr-v5-beta/41099)).

### Other announced v5 changes relevant to clients

The beta announcement also lists removal of Basic authentication in favor of Forms authentication, new OIDC options, and a new API v5. Configarr currently sends `X-Api-Key` via the shared `KyHttpClient` and the official API docs mark the API key header as required, so the authentication announcement alone does **not** establish an API-key incompatibility. Keep the API-key path, base URL handling, and reverse-proxy URL-base behavior in v5 smoke tests rather than inferring from UI authentication changes. [Beta announcement](https://forums.sonarr.tv/t/sonarr-v5-beta/41099); [v5 API docs](https://sonarr.tv/docs/api/?api=v5).

The official beta announcement doubles as Sonarr's release-note summary; it is useful for feature context, but less precise than OpenAPI for request contracts. Configarr-relevant announced items are multi-indexer release profiles, configurable pre-airdate grabbing, and expanded API v5 endpoints. New TVDB language/series-order options could affect future Configarr configuration, but are outside the current feature set. UI redesign, search/release parsing, season packs, qBittorrent tagging, and the .NET 10 upgrade do not directly change Configarr's current sync payloads. The announcement also warns that rolling back to v4 requires restoring a v4 backup, which is why the v5 e2e service has an isolated database volume.

## Feasibility in Configarr

**Assessment: feasible, with a contained but non-trivial Sonarr-specific compatibility seam.**

Configarr currently has one `SonarrClient` that imports the generated `sonarr` API and v3 resource types, calls version-3 generated methods, and implements the shared client capabilities. The common client factory dispatches only on `ArrType` (`SONARR` is one case), while `generate-api.ts` maps `sonarr` to the v3 `develop` OpenAPI URL. These are the concrete seams to evolve:

- [`src/clients/sonarr-client.ts`](../../src/clients/sonarr-client.ts) owns the v3 endpoints and generated Sonarr resource types.
- [`src/clients/client.ts`](../../src/clients/client.ts) creates one Sonarr client for `SONARR`; it currently has no Sonarr API-version discriminator.
- [`generate-api.ts`](../../generate-api.ts) generates a single `src/__generated__/sonarr` client from the v3 spec.
- The per-feature syncers consume concrete typed clients/resources. Several shared sync paths intentionally use the arr-specific generated resource type, so structurally similar schemas do not automatically make the v3 type safe for v5.

Likely changes, if v4 and v5 are to be supported at the same time:

1. **Version discovery and dispatch.** Establish a tested way to identify the Sonarr API/application version before feature sync begins, or add an explicit per-instance Sonarr API-version setting. The unversioned `/api` endpoint has an `ApiInfoResource` in both specs, and system status exposes a version string; however, neither spec by itself proves which discovery method is reliable against every beta build, proxy/base-path setup, and v4 instance. Treat detection as a design decision to validate, not as solved by the schemas.
2. **Generate and retain both clients.** Add a separate v5 spec input and generated output directory (for example `sonarr-v5`) instead of regenerating v3 files from v5 or replacing `src/__generated__/sonarr`. Pin the beta spec revision for reproducibility. The existing generator is URL-based and only has one Sonarr entry.
3. **Add a typed compatibility layer.** Keep v4 and v5 generated payloads distinct. Use version-specific client implementations/adapters for the changed settings routes and field names, download-client flags, quality-definition bulk operation and payload, and release-profile `indexerIds`. Preserve shared behavior for the payloads confirmed unchanged (quality profiles, custom formats, tags, delay profiles) where the capability interfaces permit it. Decide how the public typed `getClient("SONARR")`/`configureApi("SONARR", ...)` result represents two concrete clients before implementation; it is currently a concrete `SonarrClient`, not a version union.
4. **Define cross-version configuration semantics.** In particular, determine whether Configarr’s existing quality-definition configuration should map to v5 profile-item size properties, whether v5 still has equivalent application-wide size behavior, and how a release profile’s singular indexer config maps to v5’s array (e.g. one selected indexer versus multiple). The OpenAPI diff identifies the changed fields but does not answer these YAML/product-policy questions.
5. **Add focused client tests and Sonarr version-matrix e2e.** This was exercised locally: API path unit tests cover `/api` discovery, and the existing full Sonarr feature suite passes against both a pinned v4 image and the pinned v5 beta image. The readiness helper now discovers the v3/v5 system-status path. The CI e2e workflow still needs the pinned v5 service/readiness setup. The v5 beta announcement recommends backing up before upgrading and warns that downgrade requires restoring that backup, so the v5 test container uses disposable isolated state. [E2E suite README](../../tests/arr-e2e/README.md); [readiness helper](../../tests/arr-e2e/helpers.ts); [beta upgrade/rollback guidance](https://forums.sonarr.tv/t/sonarr-v5-beta/41099).

This approach avoids forcing v5-specific changes into the other *arr clients and keeps the v4 contract available for existing Sonarr servers. Whether to detect automatically or require explicit version configuration is a product/maintenance tradeoff: automatic detection is less user friction but needs robust fallback behavior; explicit configuration is simpler and predictable but adds config burden.

## Confirmed versus still unknown

**Confirmed by official sources**

- Sonarr announced a v5 beta on 2026-10-12, with a new v5 API; the beta announcement explicitly describes expanded API functionality and release profiles targeting multiple indexers.
- The v3 API docs are described as applying to Sonarr v3 and v4; the v5 API docs are described as applying to v5 only.
- The current OpenAPI snapshots show the route/property changes tabulated above.
- At the initial research snapshot, Configarr’s checked-out client and generator implemented/generated only the v3 Sonarr API; the dual-version adapter is described below.

**Still unknown or only verified for the pinned beta**

- The pinned v5 build accepted a `/api/v3/health` call during early probing, but the v5 docs do not promise general v3-route compatibility; Configarr now dispatches against `/api/v5`.
- The disabled-client `skipTesting`/`skipValidation=all` behavior passed the pinned build's e2e flow; later beta/final builds may change that contract.
- Whether v5 intends distinct quality-size values per profile to replace the global v4 behavior is not specified by the API diff. The adapter mapping preserves profile-specific values unless the existing global Configarr config sets them.
- The tested custom-format, profile, settings and other e2e examples passed, but they do not prove every historical user payload will satisfy v5 validation.
- API-version auto-detection through `/api` passed on the pinned local v4/v5 builds; URL-base and reverse-proxy configurations remain untested.
- The final v5 schema and behavior: the beta’s OpenAPI file is generated from a development branch and may change before final release.

## Implementation and runtime verification

This section records implementation experiments against a pinned beta rather than inferring behavior solely from the rolling OpenAPI branch.

### Pinned target and detection

- Tested `lscr.io/linuxserver/sonarr@sha256:2c1e9317f330e84a4c6e8c9295361b3a9ae425786295d8b3cfd12c7cbc008f53`, which reported Sonarr `5.0.0.2569` (`5.0.0.2569-ls193` in the image package metadata).
- The matching Sonarr source tag is [`v5.0.0.2569`](https://github.com/Sonarr/Sonarr/tree/v5.0.0.2569), commit [`57816c149d02f95543973fefb4780c4495f8121c`](https://github.com/Sonarr/Sonarr/commit/57816c149d02f95543973fefb4780c4495f8121c). The generated v5 API client is checked in separately at `src/__generated__/sonarr-v5`, sourced from this pinned version's OpenAPI document.
- Live v4 returned `{ "current": "v3" }` from `GET /api`; live v5 returned `{ "current": "v5", "deprecated": ["v3"] }`. Both `/api/v3/system/status` on v4 and `/api/v5/system/status` on v5 worked with the existing `X-Api-Key` authentication.
- This validates automatic dispatch through `/api` for the tested builds, without implying that every reverse proxy/base-path setup has been tested.

### Confirmed behavior and adapters

- v4 and v5 Sonarr containers ran side by side with separate named `/config` volumes and ports 18989/18990. The v5 test container is digest-pinned so the test target does not float with `develop`.
- The client keeps separate generated v3/v5 clients, chooses a route from `/api`, and adapts the API's version-specific payloads at the Sonarr boundary. It does not change the typed client or codepaths for other *arr applications.
- The pinned v5 naming GET/PUT payload uses `colonReplacementFormat`, same as v4, and is served at `/api/v5/settings/naming`. Media-management settings are at `/api/v5/settings/mediamanagement`; the adapter preserves v5-only fields during writes and maps nullable values to Configarr's v4-shaped client contract.
- A v5 custom-format POST using the minimal TRaSH/Configarr representation was rejected with 400: v5 requires `ImplementationName` and `InfoLink`. The v5 adapter now loads `/api/v5/customformat/schema`, enriches each requested specification with the server's implementation metadata and field definitions, then overlays configured field values. This passed both the focused `e2e-rt` custom format and a real Recyclarr template include.
- v5 quality-definition responses contain `quality`, `title`, `weight`, and `id` only; the size fields are absent. Quality-profile quality items contain `minSize`, `maxSize`, and `preferredSize`. The adapter projects only common profile-item sizes into the existing global quality-definition contract. On writes, configured global size values are applied to the corresponding item in each v5 quality profile; unconfigured values retain each profile's current value. This is the closest compatible mapping for existing Configarr YAML, but cannot express a distinct configured size per profile.
- A disabled download-client create/update worked with v5's `skipTesting` and `skipValidation=all` query parameters. The e2e client/config/remote-path test passed, confirming the practical equivalent of v4's `forceSaveIfDisabled` for this build.
- v5 release-profile writes require `airDateGracePeriod` and accept `indexerIds`. Configarr's legacy `indexerId=0` (no specific indexer) maps to an empty array; a positive legacy ID maps to one selected indexer. The tested create/update/delete flow passed. Configarr's current release-profile YAML still has a singular indexer selector and does not expose v5's multi-indexer feature.
- The requested Sonarr test suite passed against both versions: 10/10 tests for v4.0.19.2979 and 10/10 for v5.0.0.2569. Coverage includes custom formats, quality profiles, quality definitions, media settings, delay profiles, release profiles, download clients, remote paths, root folders, and a Recyclarr template include. The v5 first run exposed the custom-format metadata and release-profile required-field issues above; those were fixed before the passing run. The manual CI workflow now starts both Sonarr containers, waits for both API versions, and runs the Sonarr suite against v5 in addition to the standard suite.

### Current recommendation and remaining scope

**Recommendation: keep the dual-client, automatic `/api` discovery approach** and retain the canonical v4-shaped client capability interfaces for existing sync code. Put resource conversion only in `SonarrClient`; do not move generated v5 types into shared feature modules. This allows v4 and v5 to remain supported by one `getClient("SONARR")` result and was verified against live v4/v5 containers.

Before treating this as a finished general-availability feature, follow up on:

1. Add configuration for selecting multiple release-profile indexers if Configarr should expose the new v5 feature; the current YAML intentionally remains backward-compatible and singular.
2. Consider v5 quality-size semantics for configurations that rely on server-side v5 profiles with intentionally different sizes; the current common-value projection is necessarily lossy at the global v4-shaped interface.
3. Repeat the e2e matrix against later beta/final v5 builds as their OpenAPI and server-side validation evolve.
