# Configarr

Configarr syncs YAML config and TRaSH/Recyclarr templates to *arr apps. Sonarr and Radarr are fully supported; Lidarr, Readarr, Whisparr, and Prowlarr are experimental.

Rules below are defaults. A deviation needs the user's approval and a one-line comment in code saying why.

## Verify

`mise run check` is green before every commit. It runs the build, Biome, TypeScript, and Vitest through `pnpm check`; `pnpm lint:fix` applies safe Biome fixes.

- Unit tests use Vitest beside their source as `<source>.test.ts`, with fixtures in `tests/samples/` and mocked API clients. Keep one test file per source file.
- Sync feature changes need E2E coverage per affected app, including an idempotent second run. Follow [tests/arr-e2e/README.md](tests/arr-e2e/README.md) and run `pnpm test:e2e:arr` separately.
- Keep Sonarr v4/v5 and Radarr v5/v6/v7 working; guard version-specific features. The E2E matrix and `ARR_E2E_SEQUENTIAL` live in `vitest.arr-e2e.config.ts`.

CI time is a cost. After touching workflows, dependencies, or the build, check job timings and cache, skip by path, or parallelize new slow work.

## Stack

Follows https://github.com/BlackDark/agent-presets/blob/main/stack/core.md.

Deviations: the existing Node.js/esbuild application and Docusaurus site stay on their current stack; this tooling alignment does not migrate their runtime or docs model.

## Map

- Entry points are `src/index.ts`, the run loop in `src/run.ts`, `src/arr/*Syncer.ts`, and each feature directory.
- Media apps share `src/arr/mediaPipeline.ts`; Prowlarr has its own pipeline without quality profiles or custom formats.
- Features run load → diff → write → opt-in unmanaged cleanup. Keep dry-run and diff reporting intact.
- The instance syncer calls `getClient("SONARR")` and injects the concrete client into feature code. One handler instance per feature per run owns load, diff, write, and cleanup.
- When app fields or methods differ, use a typed `<feature>Base.ts` and thin `<feature><App>.ts` implementations constructed by that app's syncer. Identical behavior uses functions with the client as the first parameter. Prowlarr provider resources extend `src/prowlarr/providerResourceSync.ts`.
- Generic client methods live in `src/clients/capabilities.ts`; app-only methods stay on that app's client. `src/tags/` owns tags through `tags.ts` and `renderTags.ts`.

## Every change

Keep the PR scoped to the change and include only what it touches:

- Tests for changed behavior, including the affected E2E matrix for sync features.
- Updates to `docs/docs/` and `examples/` when they describe changed user-visible behavior.
- README updates for user-visible feature changes.

## Code style

- Data in, data out: pure functions, with I/O, time, and randomness passed in at the edges.
- Expected failures are values; throw only for bugs.
- Prefer composition, except where a framework or the established app-specific handler pattern requires classes.
- Split files past roughly 400 lines and functions past roughly 60 lines when the boundary improves ownership.
- Names explain what; comments explain why. Refactors preserve behavior and land in their own commit.

## Types and naming

- Use generated resources from `src/__generated__/<app>/`; regenerate with `pnpm generateApi <app>` instead of hand-editing.
- Fix mapper or class types until they fit. Use `unknown` at untyped boundaries; casts, `Merged*` cross-app types, and `any` hide mismatches. Record OpenAPI gaps with an intersection in that app's file only.
- Convert YAML/TRaSH strings to generated enums with `toEnumOrThrow` in the app mapper.
- `<feature>.types.ts` holds YAML, TRaSH, and diff types only. Use one app per file/type name and import defining modules directly without barrels.
- Config uses Zod schemas in `src/types/config.types.ts` and feature directories. Merging lives in the feature. Stay backward compatible and deprecate with a warning.
- Log through `logger` from `src/logger.ts`.

## Stewardship

Leave touched areas cleaner than found. Small fixes belong in their own commit in the same PR. Remove whatever the change makes obsolete. Report larger problems with `file:line` and a proposal without expanding the PR.

## Git

Use Conventional Commits and one topic per PR. Rebase logically separate commits; squash otherwise. Branch anew from `origin/main` after a PR merges.

`CHANGELOG.md` is generated by release-please. Use `feat:`/`fix:` for user-facing changes, `refactor:` for internal changes, `docs:`/`test:`/`style:`/`chore:` otherwise, and `ci:` or `chore(ci):` for CI fixes.
